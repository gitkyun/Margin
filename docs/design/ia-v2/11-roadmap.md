## 2. 확인을 나누는 원칙

AI(또는 구현하는 사람)는 **기계로 확인할 수 있는 것은 직접 끝내고**, 사람의 눈·판단·권한이 필요한 것만 사용자에게 요청합니다. 요청할 때는 "무엇을, 어디서, 무엇과 비교해서" 보면 되는지와 캡처를 같이 줍니다.

### AI가 직접 하는 것 (묻지 않음)

- [10](10-build-plan.md) §5의 검사 전부: `npm run typecheck`, `npm test`, `npm run test:backend`, `npm run test:sites`, `npm run build`, `node scripts/i18n-scan.mjs`, `npm run test:e2e`, `npm run format:check`, `node scripts/qa/screens.mjs`, 저장소 루트의 `python3 scripts/check_repository.py`·`python3 scripts/check_git_hygiene.py`.
- 미리보기 서버를 띄워 브라우저로 그 단계의 화면을 열어 보고, 360·390·768·1024·1440px × 라이트·다크 캡처를 찍어 PR에 붙이기. 키보드만으로 한 바퀴, 동작 줄이기 켠 상태 확인.
- [09](09-states.md)에서 그 단계 화면에 해당하는 상태 줄을 하나씩 재현해 보기(빈 상태, 실패, 권한 없음 등).
- 설계서와 코드가 다를 때: 작은 차이(문구, 간격, 순서)는 설계서를 고치고 PR 본문에 적음. 동작·권한·데이터가 바뀌는 차이는 아래 '사용자에게 요청'으로.
- 브랜치 만들기, 커밋, PR 올리기, CI 실패 고치기. `CHANGELOG.md` Unreleased 기록, 일본어 사전 추가.

### 사용자에게 요청하는 것 (멈추고 기다림)

| 언제 | 무엇을 확인받나 | 왜 사람이어야 하나 |
|---|---|---|
| 각 단계 PR 병합 전 | 주요 화면 캡처를 보고 "이대로 좋다" | 시각 판단은 사용자가 하기로 함([10](10-build-plan.md) §3) |
| PR 병합 | `main` 병합 = 실제 사이트 배포 | 병합하면 GitHub Actions가 Pages와 Supabase에 바로 배포함 |
| 2b·3b 병합 전 | 실제 AI 호출 결과(정리하기 요약·제안, 본문 수정 제안) 몇 건 | AI 답의 질은 기계 검사로 판단할 수 없음. 병합하면 `ai-assist` 함수 배포가 따라옴 |
| 2a 끝난 뒤 | 실제 학생 1~2명에게 미팅 흐름을 써 보게 할지 | 사용자의 연구실 사람을 부르는 일 |
| 설계서와 코드가 동작·권한·데이터 면에서 다를 때 | 어느 쪽을 따를지 | 제품 결정 |
| 마이그레이션이 필요해질 때 | 진행 여부 | 지금 계획(0~5단계)은 마이그레이션 없음. 생기면 계획 밖 |
| 6단계(후속) 시작 | 무엇부터 할지 | 범위 결정 |

간단한 것(검사 실패 고치기, 문구 오타, 설계서와 코드의 작은 차이, 캡처 다시 찍기)은 묻지 않고 처리한 뒤 PR 본문에 적습니다.

## 3. 단계 진행표

단계 내용은 [10](10-build-plan.md) §2, 완료 기준은 §3에 있습니다. 여기에는 진행 상태와 확인 지점만 둡니다.

| 단계 | 한 줄 | 서버 | 상태 | 사용자 확인 |
|---|---|---|---|---|
| 0 | 틀: 상단 줄(메뉴 4개), 사이드 창 틀, 휴대폰 아래 탭, 새 주소, 설정 창, 저장 대기 줄 | 없음 | [~] `feat/ia-v2-0-shell` | 캡처 검수 → 병합 |
| 1 | 공통 줄 부품, 항목 상세, 할 일 화면(T1)·할 일 창, 결정·질문 창, 홈 | 없음 | [ ] | 캡처 검수 → 병합 |
| 2a | 미팅 목록·기록 화면, 원문 선택·형광펜, 넘어온 할 일, 수정 결과 구획 | 없음 | [ ] | 캡처 검수 → 병합 → 실제 학생 사용 시험 여부 |
| 2b | [정리하기]에 본인 전사, 요약·제안 검사 | `ai-assist` | [ ] | 실제 AI 결과 + 캡처 → 병합(함수 배포) |
| 3a | 글·자료 합친 목록, 열어 둔 탭, 글 편집 틀, 자료 보기 | 없음 | [ ] | 캡처 검수 → 병합 |
| 3b | 본문 안 수정 제안 | `ai-assist` | [ ] | 실제 AI 결과 + 캡처 → 병합(함수 배포) |
| 4 | 연구 도우미 창(P1), 자료 창(P4) | 없음 | [ ] | 캡처 검수 → 병합 |
| 5 | 정리: 연구 흐름, 예전 화면·임시 통로 제거, 문서 마무리 | 없음 | [ ] | 최종 검수 → 병합 |
| 6 | 후속(사진 붙이기, 서버 전사, 형광펜 종류, 발표 자료 형태, 함께 쓰기) | 마이그레이션 | 결정 전 | 시작 여부 |

상태 표시: `[ ]` 시작 전, `[~]` 진행 중(브랜치 이름 적기), `[x]` 병합(PR 링크 적기). 단계를 끝낸 사람이 이 표를 같은 PR에서 고칩니다.

### 동시에 할 수 있는 것

- 0 → 1은 순서대로 합니다(모든 화면이 틀과 공통 줄 부품을 씀).
- 1 다음에는 **2a와 3a를 따로 진행**할 수 있습니다. 건드리는 화면이 겹치지 않습니다(미팅 / 글·자료).
- 2a와 2b는 **되도록 붙여서 배포합니다.** 2a만 있는 동안에는 녹음만 하고 메모가 없는 기록을 [정리하기]로 정리할 수 없습니다([04](04-meetings.md) §5.4의 '메모만 정리' 안내, 2026-11-17 검토).
- 2b와 3b는 둘 다 `supabase/functions/ai-assist`를 고치므로 **동시에 하지 않습니다**. 하나를 병합한 뒤 다른 하나를 그 위에서 시작합니다.
- 4는 1이 끝나면 시작할 수 있지만, 연구 도우미 요청 형태를 2b가 바꾸므로 2b 뒤가 안전합니다.
- 5는 마지막입니다.

## 4. 단계마다 반복하는 순서

1. `main`을 최신으로 받고 `feat/ia-v2-<단계>-<이름>` 브랜치를 만든다(예: `feat/ia-v2-0-shell`). `main`에 직접 커밋하지 않는다.
2. [10](10-build-plan.md) §7의 확인할 것 가운데 그 단계에 해당하는 것을 코드에서 다시 본다. 설계와 다르면 위 §2 원칙대로.
3. 만든다. 새 문구는 `t()`와 일본어 사전에 같이 넣는다.
4. §2의 'AI가 직접 하는 것'을 모두 돌린다. 실패하면 고친다.
5. PR을 올린다. 본문에 바꾼 것, 검사 결과(자동 검사 / 브라우저 화면 / 실제 AI 호출을 나눠서), 캡처, 설계서에서 고친 곳, 사용자에게 확인받을 것을 적는다.
6. 사용자 확인을 받고 병합한다. 병합 뒤 실제 사이트에서 그 단계의 주 흐름을 한 번 열어 본다.
7. 이 문서 §3 표의 상태를 고친다.
