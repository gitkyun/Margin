## 2. 확인을 나누는 원칙

AI(또는 구현하는 사람)는 **기계로 확인할 수 있는 것은 직접 끝내고**, 사람의 눈·판단·권한이 필요한 것만 사용자에게 요청합니다. 요청할 때는 "무엇을, 어디서, 무엇과 비교해서" 보면 되는지와 캡처를 같이 줍니다.

### AI가 직접 하는 것 (묻지 않음)

- [10](10-build-plan.md) §5의 검사 전부: `npm run typecheck`, `npm test`, `npm run test:backend`, `npm run test:sites`, `npm run build`, `node scripts/i18n-scan.mjs`, `npm run test:e2e`, `npm run format:check`, `node scripts/qa/screens.mjs`, 저장소 루트의 `python3 scripts/check_repository.py`·`python3 scripts/check_git_hygiene.py`.
- 미리보기 서버를 띄워 브라우저로 그 단계의 화면을 열어 보고, 360·390·768·1024·1440px × 라이트·다크 캡처를 찍어 PR에 붙이기. 키보드만으로 한 바퀴, 동작 줄이기 켠 상태 확인.
- [09](09-states.md)에서 그 단계 화면에 해당하는 상태 줄을 하나씩 재현해 보기(빈 상태, 실패, 권한 없음 등).
- 설계서와 코드가 다를 때: 작은 차이(문구, 간격, 순서)는 설계서를 고치고 PR 본문에 적음. 동작·권한·데이터가 바뀌는 차이는 아래 '사용자에게 요청'으로.
- 브랜치 만들기, 커밋, PR 올리기, CI 실패 고치기. `CHANGELOG.md` Unreleased 기록, 일본어 사전 추가.

### 사용자에게 요청하는 것 (멈추고 기다림)

| 언제 | 무엇을 확인받나 | 왜 사람이어야 하나 |
|---|---|---|
| 각 단계 PR 병합 전 | 주요 화면 캡처를 보고 "이대로 좋다" | 시각 판단은 사용자가 하기로 함([10](10-build-plan.md) §3) |
| PR 병합 | `main` 병합 = 실제 사이트 배포 | 병합하면 GitHub Actions가 Pages와 Supabase에 바로 배포함 |
| 2b·3b 병합 전 | 실제 AI 호출 결과(정리하기 요약·제안, 본문 수정 제안) 몇 건 | AI 답의 질은 기계 검사로 판단할 수 없음. 병합하면 `ai-assist` 함수 배포가 따라옴 |
| 2a 끝난 뒤 | 실제 학생 1~2명에게 미팅 흐름을 써 보게 할지 | 사용자의 연구실 사람을 부르는 일 |
| 설계서와 코드가 동작·권한·데이터 면에서 다를 때 | 어느 쪽을 따를지 | 제품 결정 |
| 마이그레이션이 필요해질 때 | 진행 여부 | 지금 계획(0~5단계)은 마이그레이션 없음. 생기면 계획 밖 |
| 6단계(후속) 시작 | 무엇부터 할지 | 범위 결정 |

간단한 것(검사 실패 고치기, 문구 오타, 설계서와 코드의 작은 차이, 캡처 다시 찍기)은 묻지 않고 처리한 뒤 PR 본문에 적습니다.

### 0단계에서 설계와 다르게 둔 것 (뒤 단계에서 맞춤)
