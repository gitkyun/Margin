# 마진 UX 라이팅 원칙

마진 화면에 들어가는 모든 문장의 기준입니다. 새 화면을 만들거나 문구를 고칠 때 이 문서와 [UI 품질 기준](ui-quality.md)을 함께 봅니다. 문구는 장식이 아니라 기능입니다. 사용자가 서비스의 동작을 정확히 알고 실수 없이 다음 행동을 하도록 씁니다.

## 1. 브랜드

| 항목 | 기준 |
|---|---|
| 서비스 이름 | **마진**. 문장·제목·버튼·알림·브라우저 제목 등 사용자에게 보이는 글에서는 한글로 씁니다. |
| 영문 표기 | 로고·워드마크 이미지, 도메인, 코드 식별자(`Margin`, `RMS`, `rms-*`)는 그대로 둡니다. 저장 키·DB 이름을 바꾸지 않습니다. |
| 슬로건 | **흩어진 기록을 모아, 다음 연구가 되도록** |
| 이전 슬로건 | ‘지난 지도를, 다음 연구로’는 더 쓰지 않습니다. |
| AI 역할 이름 | **연구 도우미**. 기능 이름이 필요할 때만 ‘AI’를 붙입니다(예: AI 사용량). |

슬로건은 소개 화면의 큰 제목·브라우저 제목·공유 문구·푸터에서만 씁니다. 작업 화면 안에서는 반복하지 않습니다.

## 2. 보이스와 톤

**보이스(늘 같음)**: 연구를 함께 정리해 주는 차분한 조교. 정확하고, 짧고, 사용자를 재촉하지 않습니다.

**톤(상황에 따라 바뀜)**

| 상황 | 톤 | 예 |
|---|---|---|
| 소개 화면 | 인상은 남기되 과장하지 않음 | 흩어진 기록을 모아, 다음 연구가 되도록 |
| 작업 화면 설명 | 정보 전달이 먼저 | 지난 피드백과 남은 할 일을 확인하세요. |
| 빈 화면 | 상태를 말하고 다음 행동 하나 | 아직 미팅이 없어요. |
| 오류 | 원인과 해결 방법 | 파일을 올리지 못했어요. 파일 형식과 크기를 확인해 주세요. |
| 완료 | 실제로 끝난 일만 | 수정 결과를 저장했어요. |
| 위험한 동작 | 결과를 분명하게 | 삭제하면 되돌릴 수 없어요. |
| 교수 화면 | 정중하고 검토에 필요한 정보 중심 | 학생이 고친 내용과 당시 파일을 확인해 주세요. |

### 말투 규칙

- **문장은 해요체**로 씁니다. ‘~합니다/습니다’, ‘~하십시오’를 쓰지 않습니다. (예외: 법적 고지 원문, 사용자가 쓴 글)
- **버튼·메뉴·탭·배지**는 짧은 명사형이나 ‘~하기’로 씁니다. ‘~해요’로 끝내지 않습니다.
- 사용자에게 시키기보다 할 수 있는 일을 알려줍니다: ‘~해야 해요’보다 ‘~할 수 있어요’, ‘~해 주세요’.
- 공포·재촉·과한 친근함을 쓰지 않습니다: ‘놓치지 마세요’, ‘함께해 볼까요?’, ‘차근차근 시작해요’, ‘멋져요!’.
- 학생이 교수를 가리킬 때 문장에서는 **교수님**, 라벨·상태에서는 **교수**를 씁니다(예: 교수 검토, 교수님께 링크를 전달해 주세요).

## 3. 핵심 원칙

### ① 명확함이 먼저

읽자마자 무엇을 할 수 있는지 알아야 합니다. 해석이 필요한 비유를 쓰지 않습니다.

- ✗ 연구의 흐름을 하나의 맥락으로 연결하세요.
- ✓ 지난 피드백과 남은 할 일을 확인하세요.

### ② 한 화면에 핵심 메시지 하나

- **제목**: 이 화면이 무엇인지
- **설명**: 지금 알아야 할 것(없으면 쓰지 않음)
- **버튼**: 누르면 일어나는 일

제목·설명·버튼이 같은 말을 반복하면 설명을 지웁니다. 허전해 보인다는 이유로 설명을 덧붙이지 않습니다.

### ③ 잡초 뽑기

빼도 뜻이 같은 단어를 지웁니다: ‘앞으로’, ‘이제’, ‘한번’, ‘손쉽게’, ‘다양한’, ‘효과적으로’, ‘~하실 수 있습니다’ → ‘~할 수 있어요’. 단, 짧게 만드는 것이 목적은 아닙니다. 기능상 필요한 조건·범위·결과는 남깁니다.

### ④ 행동과 결과를 구체적으로

- ✗ 원고는 바뀌어도, 맥락은 그대로.
- ✓ 이전 원고와 달라진 부분을 확인하세요.

다음 화면에서 무슨 일이 생기는지 예상할 수 있게 씁니다(예: ‘검토 링크 만들기’ → 링크가 만들어지고, 보내기는 직접 한다는 것을 바로 알려줌).

### ⑤ 친근하지만 차분하게

마진은 연구자가 실제로 일하는 도구입니다. 응원·축하·권유를 화면마다 반복하지 않습니다. 감정 표현은 정보를 정확히 전한 뒤 꼭 필요한 곳에만 씁니다.

### ⑥ AI가 쓴 것 같은 문장 피하기

다음은 습관적으로 쓰지 않습니다.

- 추상어 반복: 연결, 맥락, 흐름, 여정, 모든 순간, 이어가기, 하나로
- 의미가 약한 대구법·3단 나열: ‘기록하고, 고치고, 확인받는 일.’
- 감성적 수식어: 더 분명하게, 한눈에, 똑똑하게
- 내부 기획 용어: 스냅샷, 차수(설명 없이), 보존본, 근거 링크, 처리 상태

소개 화면의 큰 제목은 인상적인 문장을 쓸 수 있습니다. 작업 화면에서는 정보 전달이 우선입니다.

## 4. 정확성: 서로 다른 상태를 섞지 않기

쉬운 말로 바꾸더라도 아래 구분은 반드시 지킵니다. 이 구분은 [AGENTS.md](../../AGENTS.md)의 제품 불변 조건과 같습니다.

| 이것은 | 이것이 아님 | 쓰는 말 |
|---|---|---|
| AI 제안을 선택함 | 할 일을 끝냄 | 이 방법 선택 → 할 일로 만들기 |
| AI 제안 | 교수님의 지시 | AI 제안, 연구 도우미가 제안한 방법 |
| 검토 링크를 만듦 | 교수님께 보냄 | 링크를 만들었어요. 복사해서 교수님께 직접 전달해 주세요. |
| 교수가 ‘수정 내용 확인’을 남김 | 논문 최종 승인 | 수정 내용 확인 (승인·통과·합격 금지) |
| 할 일 완료 | 교수 검토 완료 | 완료 / 교수 응답 |
| 파일에 볼 위치를 지정함 | 그 부분만 공개함 | 먼저 볼 위치예요. 공유하면 파일 전체가 보여요. |
| 문서가 자동 저장됨 | 비교용 버전이 생김 | 저장됨 / 버전 남기기 |
| 가입 미리보기 | 실제 계정 생성 | 가입 과정 미리보기 · 실제 계정은 만들어지지 않아요 |
| 플랜 소개 | 결제 가능 | 결제는 아직 열리지 않았어요 |
| 녹음·전사 저장 | 공유 | 공개 범위는 실제 권한 설정 그대로 안내(음성을 공유해도 비공개 전사문은 공개되지 않음) |

권한·공개 범위·녹음 동의·저장 충돌·삭제 안내는 **줄이기보다 정확하게** 씁니다. 코드에서 실제 동작을 확인하고 문구를 바꿉니다.

### 시각 표기

- 시각은 접속한 기기의 시간 표시 방식을 따라 한 가지로 통일합니다: 12시간제 기기는 ‘오후 2:00’, 24시간제 기기는 ‘14:00’. 기기 설정을 읽지 못하면 24시간제로 씁니다.
- 화면 표기와 시각 입력 칸이 같은 방식을 씁니다. 직접 형식을 적지 말고 `lib/time-format.ts`의 `formatClock`·`timeParts`·`timeFieldFormat`을 씁니다.
- 저장 값(`HH:mm`, ISO 타임스탬프)은 바꾸지 않습니다.

## 5. 용어 기준

화면 문구만 바꿉니다. DB 필드·상태값·함수 이름·API 계약은 바꾸지 않습니다.

| 개념 | 쓰는 말 | 피하는 말 |
|---|---|---|
| 해야 할 일(task) | **할 일** | 작업, 이어갈 작업, 준비 작업 |
| AI가 제안한 고칠 방법 | **수정 방법** | 수정 방안, 방안 |
| AI 결과물(아직 고르지 않음) | **AI 제안** | 후보, 채택을 기다리는 결과 |
| AI 제안을 고름 | **선택**(이 방법 선택, 선택한 방법) | 채택, 채택함 |
| 피드백을 반영한 기록 | **수정 결과** | 반영 기록, 반영 완료 |
| 문서 자동 저장 | **저장**(저장 중, 저장됨) | 보존 |
| 비교용으로 남긴 문서 상태 | **버전**(버전 남기기, v2) | 스냅샷, 보존 버전, 현재 버전 보존 |
| 올린 파일(내용이 그대로 남음) | **파일**(파일 버전) | 보존 파일 |
| 외부 주소(내용이 바뀔 수 있음) | **링크** | 근거 링크 |
| 학생이 교수에게 확인을 부탁함 | **검토 요청** | 검토 의뢰, 공유 요청 |
| 같은 항목을 다시 확인받음 | **다시 확인 요청**, **2차 검토** | 재확인 차수 생성 |
| 교수 결과 | **수정 내용 확인** / **추가 수정 필요**(이유 필수) | 승인, 반려, 통과 |
| 함께 연구하는 학생 | **공동연구자** | 참여자(설정 화면의 권한 설명에서만) |
| 미팅 중 받은 말 | **피드백** | 지적 사항, 코멘트 |
| PDF에서 교수님이 먼저 볼 곳 | **볼 위치** | 확인 위치(검토 결과 ‘확인’과 헷갈림) |
| 올린 파일을 자료로 남기는 단계 | **등록**(등록 다시 시도) | 연결(기록 사이의 관계에만) |
| AI 답변을 얼마나 자세히 할지 | **답변 깊이**: 간단히 · 보통 · 자세히 | 검토 깊이(검토는 교수 검토), 차근차근, 꼼꼼하게 |
| 일정 조율에서 고를 시간 | **후보 시간** | – (AI 결과가 아니므로 ‘후보’를 써도 됨) |

### 상태 라벨

| 대상 | 라벨 |
|---|---|
| 할 일 | 시작 전 · 진행 중 · 완료 |
| 피드백 | 시작 전 · 진행 중 · 수정 결과 있음 · 보류 · 고치지 않음 |
| 미팅 | 준비 중 · 기록 중 · 기록 완료 · 취소 |
| 연구 단계 · 주요 목표 | 예정 · 진행 중 · 완료 |
| AI 실행 | 실행 중 · 성공 · 실패 · 중단 |
| 수정 결과(목록) | 검토 요청 전 · 검토 요청 N건 |
| 검토 공유 | 공유 중 · 공유 중지 |
| 교수 응답 | 수정 내용 확인 · 추가 수정 필요 |

상태가 다르면 라벨도 다르게 둡니다. ‘완료’는 사용자가 직접 끝냈다고 표시하는 할 일·연구 단계·주요 목표에만 씁니다. AI 실행이 끝난 것은 ‘성공’, 교수의 결과는 ‘수정 내용 확인’입니다.

### 표기

- 숫자와 단위는 붙입니다: 2개, 3건, 20MB, 11월 11일 (수).
- 가운뎃점(·)은 짧은 라벨 묶음에만 씁니다(계획·일정). 문장 안에서 나열이 셋 이상이면 쉼표를 씁니다.
- ‘AI’, ‘PDF’, ‘URL’은 영문 그대로. 사용자에게 ‘URL’보다 ‘링크’가 낫습니다.
- 말줄임표(…)는 로딩에 쓰지 않습니다: ‘저장 중’, ‘불러오는 중’.

## 6. 요소별 작성 규칙

### 화면 제목

- 무엇을 하는 곳인지 명사구로: ‘할 일’, ‘검토 요청’, ‘연구 설정’.
- 마침표를 쓰지 않습니다. 소개 화면의 큰 문장형 제목만 예외입니다.

### 설명

- 한두 문장, 해요체, 마침표.
- 제목을 다시 말하지 않습니다. 없어도 되면 지웁니다.

### 버튼

- 누르면 일어나는 일을 씁니다: 저장, 삭제, 연구 만들기, 검토 링크 만들기.
- 확인 창의 주 버튼은 제목의 동사와 맞춥니다: ‘연구를 삭제할까요?’ → [삭제].
- 닫기만 하는 버튼은 ‘닫기’, 작업을 그만두는 버튼은 ‘취소’.
- 진행 중 상태는 ‘저장 중’, ‘만드는 중’처럼 같은 자리에서 바꿉니다.

### 탭·메뉴·필터

- 2~6자 명사. 서로 겹치는 말을 쓰지 않습니다.
- 필터 칩과 상태 배지는 다른 모양·문구로 구분합니다.

### 빈 화면

- 상태 한 문장 + (필요하면) 다음 행동 버튼 하나.
- ‘~이 없어요.’ 형태. 질문형 권유(‘~해 볼까요?’)를 쓰지 않습니다.
- ✗ 다음 미팅을 준비해 볼까요? ✓ 다음 미팅이 아직 없어요. [미팅 만들기]

### 성공

- 실제로 끝난 동작만, 과거형: ‘저장했어요’, ‘링크를 복사했어요’.
- 다음에 사용자가 해야 할 일이 있으면 이어서 씁니다: ‘링크를 복사했어요. 교수님께 직접 전달해 주세요.’
- 축하·감탄을 붙이지 않습니다.

### 오류

- **무엇이 안 됐는지 + 왜(알 수 있으면) + 어떻게 하면 되는지**.
- 입력이 남아 있는지 알려줍니다: ‘입력한 내용은 그대로 있어요.’
- 개발 용어·코드를 보여주지 않습니다(JWT, 409, fetch 등).
- 사용자가 스스로 해결할 수 없으면 그렇다고 말하고 할 수 있는 일을 줍니다.
- ✓ 다른 창에서 내용이 바뀌었어요. 지금 쓴 내용을 복사해 둔 뒤 새로고침해 주세요.

### 확인 창

- 제목은 질문: ‘~할까요?’
- 설명에는 결과와 되돌릴 수 있는지: ‘휴지통으로 옮겨요. 휴지통에서 되돌릴 수 있어요.’ (기간·자동 삭제처럼 실제로 없는 동작을 쓰지 않습니다.)
- 버튼: [취소] [동사].

### 로딩

- ‘불러오는 중’, ‘저장 중’, ‘연구 도우미가 정리하는 중’. 진행률·남은 시간을 지어내지 않습니다.

### 플레이스홀더·도움말

- 예시나 입력 형식만: ‘예: 선행연구 비교표 보완’. 라벨을 대신하지 않습니다(라벨은 항상 따로 둡니다).

### 접근성 이름

- 보이는 글자가 있으면 `aria-label`을 따로 두지 않거나, 보이는 글자로 시작하게 씁니다(WCAG 2.5.3).
- 아이콘만 있는 버튼은 동작을 씁니다: ‘알림 3개 보기’, ‘메뉴 열기’.
- 같은 화면의 같은 동작은 같은 이름을 씁니다.
- 로고 링크는 ‘마진(Margin) 홈’처럼 한글 브랜드와 보이는 영문 워드마크를 함께 담습니다(보이는 글자가 이름에 들어가야 음성 명령으로 누를 수 있음).

### 개발 시 주의

- 폼 대화상자의 닫기 감지(`FormNavigationGuard`)는 글자가 정확히 ‘취소’인 버튼을 찾습니다. 취소 버튼 이름을 바꾸거나 다른 버튼을 ‘취소’로 바꾸면 동작이 달라집니다.
- 한글 입력 중 Enter로 제출·선택하는 입력란은 `e.nativeEvent.isComposing`을 확인합니다(조합 중 Enter 무시).
- 서버(DB 함수·Edge Function)가 보내는 오류 문구는 `src/lib/server-messages.ts`에서 이 문서 기준으로 바꿔 보여줍니다. 서버 문구를 새로 만들면 여기에도 추가합니다.

## 7. 학생 화면과 교수 화면

| | 학생 화면 | 교수 화면 |
|---|---|---|
| 목적 | 기록·할 일·수정 관리 | 지정된 항목 검토 |
| 문장 | 해요체, 행동 중심 | 해요체, 정중하게, 판단에 필요한 정보 중심 |
| 보여줄 것 | 내 상태, 다음 할 일 | 항목, 학생 설명, 당시 파일, 볼 위치, 차수 |
| 숨길 것 | – | 학생의 개인 메모, AI 대화, 선택하지 않은 AI 제안 |
| 결과 | – | 수정 내용 확인 / 추가 수정 필요(이유 필수) |

교수 화면에는 학생 쪽 내부 용어(할 일 상태, AI 제안 등)를 쓰지 않습니다.

## 8. 고친 사례

| 위치 | 이전 | 이후 | 이유 |
|---|---|---|---|
| 슬로건 | 지난 지도를, 다음 연구로 | 흩어진 기록을 모아, 다음 연구가 되도록 | 확정된 슬로건 |
| 연구 홈 | 이어갈 작업 | 남은 할 일 | 용어 통일, 상태가 바로 보임 |
| 피드백 | 수정 방안 | 수정 방법 | 쉬운 말 |
| AI | 방안 채택 | 이 방법 선택 | 쉬운 말, 선택 ≠ 완료 |
| AI | 채택을 기다리는 결과 | 확인할 AI 제안 | 행동 중심 |
| 글쓰기 | 현재 버전 보존 | 지금 버전 남기기 | 저장과 버전 구분 |
| 연구 홈 | 다음 미팅을 준비해 볼까요? | 다음 미팅이 아직 없어요. | 빈 화면은 상태부터 |
| 소개 | 여러 기록, 하나의 맥락. | 지난 피드백을 쉽게 찾아요. | 추상어 제거 |
| 알림 | 새 소식을 모두 확인했어요. | 확인할 새 소식이 없어요. | 실제 상태 |
| 계획 | 연구의 큰 흐름과 다음 약속을 함께 살펴보세요. | 연구 단계와 중요한 일정을 확인하세요. | 추상어 제거 |
| 공통 | 이 연구를 열 수 없습니다. | 이 연구를 열 수 없어요 | 해요체, 제목에 마침표 없음 |
| 피드백 상태 | 반영 기록 있음 | 수정 결과 있음 | 뜻이 바로 보임 |
| 피드백 상태 | 미수정 결정 | 고치지 않음 | 쉬운 말 |

실제 반영된 전체 목록은 커밋과 [변경 내역](../../CHANGELOG.md)에서 확인합니다.

## 9. 새 화면 체크리스트

문구를 넣거나 고칠 때 아래를 모두 확인합니다.

1. 이 문장이 없어도 사용자가 같은 행동을 할 수 있다면 지웠나요?
2. 제목·설명·버튼이 같은 말을 반복하지 않나요?
3. 해요체인가요? 버튼·탭·배지는 명사형/‘~하기’인가요?
4. 용어표의 말을 썼나요(할 일, 수정 방법, AI 제안, 선택, 버전, 검토 요청)?
5. 4장의 구분을 흐리지 않나요(선택 ≠ 완료, 링크 생성 ≠ 전송, 확인 ≠ 승인, 저장 ≠ 버전)?
6. 오류에 원인과 해결 방법, 입력 유지 여부가 있나요?
7. 완료 문구가 실제로 끝난 동작만 말하나요?
8. 교수 화면에 학생 내부 용어·비공개 정보가 없나요?
9. 보이는 글자와 접근성 이름이 같은가요?
10. 360px부터 1440px까지, 라이트·다크에서 줄바꿈·잘림·겹침이 없나요? ([UI 품질 기준](ui-quality.md))
