## 작업 1 — U8-01 글자를 고르면 AI 바가 포커스를 가져가는 문제 (P1)

```text
## 작업: 편집기 선택 바가 포커스를 가져가지 않게 한다
현상(실측, 실제 마우스 드래그로도 재현): 문서 본문을 드래그로 선택하면 플로팅 AI 바가 뜨고, 그 즉시 document.activeElement가 바의 입력칸(placeholder "어떻게 고칠까요?")으로 옮겨가 선택 길이가 0이 된다. Shift+↓로 선택을 넓힐 수 없고 Ctrl/⌘+B가 안 먹고 치는 글자가 AI 지시칸에 들어간다.
원인 후보(코드 확인, 파일을 직접 열어 확인할 것):
- src/components/kokonut/ai-inline-edit.tsx 의 InlineEditBar 안 useEffect(약 1372~1376줄): phase가 "prompt"이면 inputRef.focus()를 호출한다.
- 사용처: src/pages/writing/WritingReview.tsx 의 selectionBar(약 571~619줄)에서 phase="prompt"로 렌더한다.
고칠 방법(최소 변경):
1. InlineEditBar에 선택 prop `focusPrompt?: boolean`(기본 true, 다른 사용처 동작 유지)을 추가한다. false면 prompt 단계에서 입력칸에 포커스를 주지 않는다. review 단계에서 '반영' 버튼으로 포커스가 가는 기존 동작은 유지한다.
2. WritingReview.tsx는 `focusPrompt={false}`로 넘긴다.
3. 키보드로 입력칸에 들어갈 명시적 진입을 하나 둔다: focusPrompt가 false이고 prompt 단계일 때 `⌘/`(Ctrl+/)를 누르면 입력칸에 포커스가 가고 기본 동작은 막는다(isComposing 중에는 무시). 바 그룹 요소에 aria-keyshortcuts를 단다. 입력칸을 클릭하면 당연히 들어갈 수 있어야 한다.
완료 기준:
- 문단을 마우스로 선택한 뒤 document.activeElement가 .ProseMirror 안에 있고 getSelection().toString().length > 0 이다. Shift+↓로 선택이 늘어나고, 선택 상태에서 글자를 치면 선택이 대체된다(문서로 들어감).
- 입력칸 클릭과 ⌘/ 두 방법으로 바 입력칸에 들어가고, Enter로 실행, Escape로 닫기가 그대로 된다.
- InlineEditBar를 쓰는 다른 곳이 있으면 동작이 그대로다(기본값 true).
- 가능하면 이 prop 동작을 확인하는 vitest를 추가한다(기존 컴포넌트 테스트 방식을 먼저 찾아본다. 없으면 그렇게 보고한다).
```

## 작업 2 — U8-03 선택 바가 스크롤을 따라오지 않는 문제

```text
## 작업: 편집기 선택 바가 선택한 글자를 따라다니게 한다
(작업 1이 끝난 뒤 하는 것을 권장한다. 같은 파일을 만진다. 앞 작업의 변경을 되돌리지 않는다.)
현상(실측): 글자를 선택해 바가 뜬 뒤 페이지를 스크롤하면 본문은 움직이는데 바의 화면 위치는 그대로다(scrollY 0과 70에서 같은 좌표). 선택한 글자와 바가 떨어진다.
원인(코드 확인): src/pages/writing/WritingReview.tsx 의 toolbarPosition(약 548~564줄)이 렌더 때 editor.view.coordsAtPos로 한 번 계산되고, 스크롤·리사이즈에는 다시 계산하지 않는다. 바는 position:fixed다.
결정(사용자): 화면에서 익숙한 방식을 따른다. 바는 선택 영역 아래에 붙어 따라다니고, 선택이 화면 밖으로 나가면 화면 안쪽 가장자리에 걸쳐 있게 한다(기존 clamp 유지).
고칠 방법: 바가 보이는 동안(selectedText 또는 inlineEdit 있음) window와 스크롤 가능한 조상의 scroll(capture)과 resize를 듣고, 위치를 다시 계산하게 한다(상태 tick을 올려 재렌더 등 가장 단순한 방식). 이벤트는 바가 사라질 때 정리한다. 성능을 위해 requestAnimationFrame으로 묶는다.
완료 기준: 선택 후 70px 스크롤하면 바의 y가 같은 만큼 움직인다(clamp에 닿을 때까지). 리사이즈 후에도 선택 아래에 있다. 바가 사라지면 리스너가 남지 않는다. 기존 diff 미리보기 위치(toolbarPosition 사용 부분)도 함께 따라간다.
```

## 작업 3 — U4-01 미팅·기록 목록 왼쪽 열 220px

```text
## 작업: 미팅 목록 왼쪽 열이 220px에 고정돼 글자가 잘리고 오른쪽이 비는 문제
현상(실측, 1920 폭): .meetings-layout의 grid-template-columns가 "220px 1012px"이고 전체 폭은 1256px이다. 목록 열이 220px라 행의 부제(날짜·상태·'다음' 배지)가 좁게 눌리고, 아무것도 선택하지 않은 오른쪽 1012px는 빈 면이다. 행 내부 텍스트 상자는 약 109~152px다.
원인 후보(코드 확인): src/components/meetings/record-list.css 의 .meetings-layout 의 `220px minmax(0,1fr)`(약 218줄 부근). 같은 부품을 홈 최근 미팅과 기록 목록이 쓸 수 있다. 행 오른쪽의 ⋯ 버튼이 opacity 0이어도 자리를 차지한다는 보고가 있다(미확인).
고칠 방법(최소): 왼쪽 열을 고정 220px 대신 폭에 따라 늘어나게 한다(예: clamp 또는 minmax 사용, 최대 약 320px). 좁은 폭(1280, 1024, 모바일 시트 구성)의 기존 동작은 바꾸지 않는다. 행의 제목·부제 말줄임 규칙은 그대로 둔다.
완료 기준(수치): 1920 폭에서 왼쪽 열 ≥ 280px이고, 부제 텍스트(예: "11월 21일 (토) · 기록 없음", '다음' 배지가 붙은 행)가 말줄임 없이 보인다. 1280·1024 폭에서 이전과 같은 배치다. 이 목록 부품을 쓰는 다른 화면(홈 최근 미팅 등)을 grep으로 찾아 영향이 없는지 보고한다. 오른쪽 빈 상태 면은 이번 작업에서 바꾸지 않는다.
```

```text
## 작업: 기록 탭 오른쪽 열에서 AI 제안이 한없이 쌓이는 문제
현상(실측): 미팅 상세의 .record-side 높이가 5554px이고 그중 '피드백·할 일' 섹션이 4664px다. 결정·질문·형광펜 구획이 그 아래로 밀려 5000px 넘게 내려가야 보인다(문서 높이 5901px).
```

## 작업 5 — U5-01 원문 번호 배지가 글자를 덮는 문제

```text
## 작업: 미팅 원문 메모의 번호 배지가 다음 글자를 덮는 문제
현상(실측): .memo-anchor-num이 width:0이고 글리프 상자는 18×18이다. 예: 배지 (741,163)–(759,181), 바로 뒤 글자 상자 (740,174, 32×19) → 세로 7px가 겹친다. 같은 위치에 번호 2개가 같은 문장에 붙으면 완전히 포개진다는 보고도 있다(U5-02, 이 시연 데이터에서는 재현 못 함).
원인 후보(코드 확인): 원문 오버레이 CSS의 .memo-anchor-num `width:0; bottom:0.7em`(record-side.css 264~276줄 부근, 직접 확인할 것). 결정·질문의 원문 링크도 같은 기준점을 쓴다.
고칠 방법(최소): 배지가 줄 높이 안에서 글자와 겹치지 않게 한다(예: 글자 위로 올려 위첨자처럼 두거나 배지 폭만큼 오른쪽 여백을 확보). 위치 규칙은 한 곳(.memo-anchor-num)에서 바꾼다. 같은 문장에 번호가 여러 개면 가로로 이어지게 하거나 서로 겹치지 않게 간격을 둔다.
완료 기준: 브라우저 콘솔에서 배지 글리프 상자(Range.getBoundingClientRect)와 바로 뒤 글자 3자 range 상자의 교차 면적이 0이다(사용자가 확인). 앞 줄 글자와도 겹치지 않는다. 번호의 의미·색·클릭 동작은 바꾸지 않는다.
```

## 작업 6 — U6-04 할 일 상세 패널의 가로 넘침

```text
## 작업: 할 일 상세에서 긴 연결 피드백 제목이 패널 밖으로 밀어내는 문제
현상(실측, 오른쪽 상세 패널 폭 312px, /r/:id/tasks?detail=task:<id>): .item-detail-body의 scrollWidth 324 > clientWidth 312(12px 넘침). '연결된 피드백' 항목(.item-detail-task) scrollWidth 308 > 280. 제목(약 100자) span의 scrollWidth 964, 보이는 상자 240px. 그 옆 '연결 해제'류 버튼의 오른쪽 끝이 1872로 패널 오른쪽 끝 1860보다 12px 밖이다.
원인 후보: 연결된 피드백 행이 flex이고 제목 span이 한 줄 고정이며 min-width:0이 없다(파일을 직접 찾을 것. 클래스 .item-detail-task, .item-detail-section).
고칠 방법(최소): 제목이 줄어들게(min-width:0) 하고 줄바꿈 또는 말줄임(2줄 정도)을 적용한다. 버튼은 항상 패널 안에 보인다. 접근 가능한 이름과 title(전체 제목)은 유지한다.
완료 기준: 위 상세에서 .item-detail-body.scrollWidth === clientWidth, 버튼 오른쪽 끝 ≤ 패널 오른쪽 끝이다. 제목이 짧은 항목은 이전과 같다.
```

## 작업 7 — U2-03·U2-04 입력 오류 문구

```text
## 작업: 입력 오류가 이유 없이 빨간 테두리만 있거나 회색으로 나오는 문제
현상 1(U2-03, 실측): /r/new 1단계 '지도교수 이메일'에 abc를 넣고 Enter를 치면 입력에 aria-invalid="true"가 걸리고 .email-chips 테두리가 rgb(255,66,66) 1px로 바뀌지만, 이유를 말하는 문구가 없다. aria-describedby는 일반 안내문('Enter나 쉼표로 한 명씩 넣어요. …')만 가리킨다.
현상 2(U2-04, 코드 보고, 직접 확인할 것): 설정 창 '연구 정보'에서 이름을 비우거나 지난 목표일을 넣으면 오류 문구가 회색으로 보인다. experience.css의 `.field small`이 styles.css의 `.field-error`를 덮는다. 공용 LabeledInput 전체에 영향.
고칠 방법(최소):
1. 이메일 칩 입력에서 형식이 틀린 입력일 때 입력칸 아래에 이유 문구를 보이고(예: "이메일 주소 형식을 확인해 주세요." — docs/design/ux-writing.md의 어조와 용어를 따를 것) 입력의 aria-describedby에 연결한다. 올바른 이메일을 넣거나 지우면 사라진다.
2. 오류 문구 색이 Montage의 위험(danger) 텍스트 토큰으로 보이게 CSS 우선순위를 고친다(새 hex 금지, 기존 --danger 계열 토큰 사용). 한 부품에서 고쳐 LabeledInput을 쓰는 모든 곳에 적용되게 한다.
```
