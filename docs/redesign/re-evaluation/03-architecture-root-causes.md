## RC-1. 역할 모델에 '보내는 쪽 / 받는 쪽' 구분이 없다

**증상**
- 겸임 교수의 검토 화면에 `공유 설정`, `다시 확인 요청`, "교수님께 메일로도 알리기"(발신 UI)와 "내가 남긴 응답"(수신 UI)이 함께 보인다(P02-2).
- 겸임 교수 `/r`에서 `+ 연구 만들기`가 가장 강조된다(P01-3).
- 겸임 교수 홈에 '시작하기 3/4'가 다시 뜬다(P03-2).
- 겸임 교수의 알림 부제가 학생용 문구다(P08-3).
- 신규: 겸임 교수가 자기에게 온 검토의 받는 교수 이메일을 바꾸고 재확인 차수를 만들 수 있다.

**[확인된 원인]**
- 클라이언트: `lib/review-permissions.ts:36-44`의 `canManageResearch`는 "소유자이거나 활성 멤버(편집자 포함)"다. 검토 화면은 이 값을 `isOwner`라는 이름으로 받는다(`pages/reviews/ReviewDetailPage.tsx:522`). 그리고 발신 UI 전부를 이 값으로 연다. 이름은 '소유자'인데 실제 의미는 '편집 가능자'다.
- 수신 쪽은 `isAssignedProfessor`(`review-permissions.ts:45`)로 따로 계산한다. 두 값이 동시에 참일 때 어느 쪽 UI를 보일지 정하는 우선순위가 없다. U10-01은 응답 폼이 사라지지 않게 하는 것까지만 다뤘다.
- 서버: `rms_set_sharing`(`202611030001_rms.sql`)과 `rms_recheck`(`20261104131740_experience_expansion.sql`)는 `rms_can_edit_research`만 검사한다. 지정 교수 본인인지는 보지 않는다. `rms_set_sharing`은 `professorEmail`이 다르면 `professor_id`를 새로 지정한다.
- 결정 D1(2026-11-22, `docs/qa/2026-11-22-qa-11th-verification.md:51`)이 "서버 권한은 바꾸지 않는다"로 정했다. 위 서버 동작은 그대로 유지됐다.
- 역할을 모르는 다른 판단들:
  - 온보딩 체크리스트는 '지금 사용자에게 보이는 데이터'로만 판단한다(`lib/onboarding.ts:68-115`, `pages/HomePage.tsx:150-155`).
  - 알림 부제는 `data.researches.length === 0`으로 학생과 교수를 가른다(`components/WorkspaceShell.tsx:615`). 연구가 하나라도 보이는 교수는 학생으로 취급된다.
  - `/r`의 CTA는 `incomingOnly`(검토만 받은 교수)일 때만 숨긴다(`pages/AuthPages.tsx:254-255`).

**[추정 원인]** 제품 초기 모델이 "학생 = 연구 소유자, 교수 = 외부 검토자"로 둘이 겹치지 않았다. 11-11 프로젝트 초대(`20261111150000_project_invites.sql`)로 겹침이 가능해졌지만, 역할 판정 함수는 그대로 남은 것으로 보인다.

**영향 범위**: 검토 화면 전체, 홈 온보딩, 알림, `/r` 허브, 서버 RPC 2개. 사용자 결정으로 **재검토 안건**이다.

**[Phase 5 질문]**
- 한 연구 안에서 같은 사람이 '지정 교수'이자 '편집자'일 때, 화면은 어느 역할을 우선할까?
- 지정 교수가 자기 검토의 공유 설정과 재확인을 바꾸지 못하게 하는 규칙을 클라이언트와 서버 양쪽에 둘까?
- 역할 판정을 화면마다 하지 않고 하나의 함수(예: '이 연구에서 나는 무엇인가')로 모을까?

## RC-2. 위험 동작의 확인 방식을 정하는 공통 규칙이 없다

**증상**
- 휴지통 이동은 연구 카드에서는 이름 입력, 설정에서는 일반 확인이다(P04-1).

- 완전 삭제는 슬라이더다(P04-1, #5).
- 모든 확인 창에 ✕와 `취소`가 함께 있다(P04-4).
- 슬라이더 끝단이 직선이다(P05-1).
- 휴지통 카드의 위험 위계가 약하다(P06-4).
- 삭제 설명이 3줄이다(P08-4).

**[확인된 원인]**
- 확인 UI가 화면마다 따로 구현돼 있다.
  - 휴지통 동작 **목록**은 `lib/research-card-actions.ts`를 함께 쓴다.
  - 하지만 **확인 창과 실행**은 `pages/AuthPages.tsx:665-720`(이름 입력, 실행 681행)과 `pages/SettingsPage.tsx:1047-1135`(일반 확인, 실행 1113행)에 각각 있다.
- 확인 수단이 세 종류이고, 쓰임새를 정한 규칙이 없다.
  - `SlideToConfirm`: `PermanentResearchDelete.tsx`, `ReviewDetailPage.tsx`(공유 중지)
  - `useConfirm`: 9개 파일
  - 화면별 직접 구현: `AuthPages`의 이름 입력
- 불변 조건 `AGENTS.md:21`이 완전 삭제에 '슬라이드 확인'을 수단까지 지정한다. 위험도 원칙이 아니라 구체 컴포넌트를 박아 둔 것이다.

**영향 범위**: 연구 수명주기(보관·휴지통·복원·완전 삭제), 검토 공유, 모든 확인 창. 사용자 결정:

## RC-5. AI 시작 칩 생성 규칙이 거꾸로 동작한다

**증상**: 홈은 칩 1개, 미팅 화면은 3개, PDF는 3개다. 그런데 PDF의 3개는 맥락과 무관한 일반 예시다(P03-1, P03-S3, #13).

**[확인된 원인]**
- `pages/ResearchAssistant.tsx:1569-1571`: `starters.length ? starters : GENERIC_STARTERS`. 맥락 추천이 하나라도 있으면 예시 3개를 통째로 빼고, 없으면 예시만 보인다. 합치지 않는다.
- 맥락 추천은 `lib/assistant-starters.ts`에서 만든다(최대 3). 홈 분기는 미완료 할 일이 있을 때 `week` 1개뿐이고, 자료·PDF 화면 분기는 없다.
- 그래서 맥락을 많이 아는 화면일수록 칩이 적고, 맥락이 없는 화면은 엉뚱한 예시("이 피드백은…")를 보인다.

- `[확인된 사실, 강점]` `⋯` 메뉴와 우클릭 메뉴 항목이 같다(7개, 구분선 2). Esc로 닫으면 포커스가 `⋯` 버튼으로 돌아간다. `폴더에서 빼기`는 폴더 안 행에만 붙는다(`DocsPage.tsx:265`). `보관`은 되돌리기 토스트가 있다(`DocsPage.tsx:156-159`).
