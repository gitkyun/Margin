## 5단계 전에 먼저 다룰 문제

원고는 복원 전 상태가 빠짐없이 남는지부터 확인해야 한다. 할 일은 기록에서 생성한 항목을 목록에서도 같은 출처로 찾을 수 있어야 한다. 두 흐름이 끊기면 버튼이나 화면의 배치를 다듬어도 사용자는 작업이 저장됐는지 판단하기 어렵다.

## 직접 확인한 추가 문제

### 원고 복원 직전 제목과 서식 유실

가상 원고의 v1을 남긴 뒤 제목과 본문의 굵기만 바꿔 저장했다. v1을 복원하자 체험 모드와 격리 연결 모드에서 제목과 굵기가 모두 v1 상태로 돌아갔다. 새 이력에도 복원 직전의 제목과 굵기가 남지 않았다. 저장된 값과 버전 목록을 모두 확인했다. 복원 전 상태를 남길지 판단하는 조건이 본문 글자만 비교한다. ‘지금 내용은 지우지 않고’라는 안내가 성립하려면 제목·본문 구조·서식까지 보존 여부를 확인해야 한다. [복원 직전](캡처/연결/02-new-title-format-before.png) · [비교 화면](캡처/연결/03-18-compare-no-title-format.png) · [복원 뒤 이력](캡처/연결/04-new-title-format-after.png) · 원고 코드 (`../../../Margin-repo/apps/home-preview/src/pages/WritingPage.tsx`, 저장소에 없음)

### 복원 실패 뒤 화면과 저장본 불일치

본문까지 바뀐 원고에서 마지막 버전 기록 요청 한 건에 실패를 넣었다. 화면에는 오류와 복원 직전 제목이 남았고, 저장소에는 이미 과거 제목·본문이 들어가 있었다. 새로고침하니 과거 원고가 나왔다. 이 사례에서 복원 직전 상태는 v2에 남았다. 복원에 필요한 쓰기를 한 단위로 처리하거나, 부분 저장 뒤 상태를 정확히 알려 주고 같은 작업을 다시 시도해도 이력이 꼬이지 않게 해야 한다. [실패 직후](캡처/연결/05-new-restore-failed-version.png) · [새로고침 뒤](캡처/연결/06-new-restore-after-refresh.png)

### 저장 중에 바꾼 공개 범위 미반영

이미 공유 중인 가상 원고의 첫 본문 저장을 지연시키고, 응답이 오기 전에 ‘나만 보기’를 골랐다. 응답 뒤 화면에는 ‘나만 보기 · 저장됨’이 표시됐지만 새로고침하면 ‘공동연구자와 공유’로 돌아왔다. 격리 저장소에서 공동연구자도 계속 접근할 수 있었다. 원고 저장 응답은 뒤이어 바뀐 제목·공개 범위를 확인하지 않고 본문이 같으면 변경 표시를 지운다. 공개 정책의 변경 없이 저장 직후의 제목·본문·공개 값을 함께 검증할 수 있다. [응답 뒤](캡처/연결/07-new-visibility-stale.png) · [새로고침 뒤](캡처/연결/08-new-visibility-reload.png)

### 기록에서 만든 할 일의 출처 불일치

가상 ‘5차 지도 기록’에서 ‘원고 2장 표의 출처 추가’를 만들었다. 기록 상세에는 나타났고 저장소에도 출처가 있었다. 할 일 목록은 ‘직접 추가’로 표시했고, 기록 필터에서 ‘가상 5차 지도 기록’을 고르자 항목이 사라졌다. 필터를 풀면 다시 나타났다. 출처를 읽는 방식이 기록과 목록에서 다르다. 기록에서 직접 만들기, 피드백에 연결하기, 다음 미팅에 가져가기의 세 경로마다 출처와 참조 관계를 확인해야 한다. ### 실행 요청과 크레딧의 잘못된 안내

사용량 화면에 ‘월간 한도는 없고, 최근 24시간 한도만 있어요.’가 표시된다. 현재 저장 규칙은 월 크레딧을 사용하고 기존 24시간 100회 제한을 제거했으며 분당 6회 제한은 유지한다. 백엔드 검사에서는 2시간 전 101회 요청 뒤 새 요청이 허용되고 1분 안의 일곱 번째 요청이 제한되는 것을 검증한다. 같은 화면의 ‘선택한 기록과 질문만’도 일반 질문의 범위를 설명하기에는 좁다. 일반 질문에는 사용자가 읽을 수 있는 연구 기록이 들어갈 수 있고, 공개 웹 검색에 보내는 내용은 질문이다. 실제 호출 종류에 맞춰 전송 범위와 사용량을 알려 주는 게 맞다. ### 완료 취소가 화면마다 다른 할 일

코드에서 홈·할 일·기록 패널은 완료를 풀면 ‘진행 중’으로 보내고, 원고 여백과 항목 상세는 ‘시작 전’으로 보낸다. 일반 목록에서 보이는 완료 직후의 되돌리기도 두 화면에는 없다. 동일한 할 일을 서로 다른 화면에서 완료하고 취소할 때 같은 상태로 돌아가는지 확인한 뒤 공통 동작을 정하는 편이 좋다. 두 할 일 영역이 단축키에 동시에 반응할 가능성은 코드에서 찾았고 브라우저 재현은 별도다. 공통 완료 처리 (`../../../Margin-repo/apps/home-preview/src/lib/use-task-completion.ts`, 저장소에 없음) · 원고 처리 (`../../../Margin-repo/apps/home-preview/src/pages/WritingPage.tsx`, 저장소에 없음) · 상세 처리 (`../../../Margin-repo/apps/home-preview/src/components/item-detail/ItemDetail.tsx`, 저장소에 없음)

## 앞선 판단에 반영할 내용

- **원고와 검토 이력**은 새로운 비교 화면을 결정하기 전에 보존 기준을 먼저 맞춰야 한다. 저장 전 변경, 복원 직전 상태, 저장 실패 뒤 다시 시도, 삭제한 댓글의 답글은 화면을 바꿔도 남겨야 할 서로 다른 데이터다.
- **할 일과 피드백**은 목록·원문·사이드 패널이 읽는 기준이 나뉘어 있다. 기록에서 만든 할 일, 기록에 가져간 할 일, 피드백에 붙은 할 일 각각을 만들어 목록·필터·다음 미팅 요약에서 찾을 수 있게 확인한다.
- **공통 화면 요소**는 앞선 레퍼런스와 라이브러리 기본값으로 판단할 수 있다. 같은 제품의 날짜·선택 상자·경고·재시도 버튼이 상황마다 달라지는 부분부터 본다. 예를 들어 할 일 기록 필터의 접근성 이름은 실제로 ‘모든 기록, 모든 기록’이었다. 기존 패널 폭에서 글자와 눈금이 읽히는지도 같이 시험한다.
- **교수 검토와 공유**는 같은 사용자 역할을 전면 재설계할 근거가 이번 문서에서 추가되지 않았다. 이번에 의미 있는 것은 공개 버튼의 결과, 핀 위치 선택 취소, 댓글 삭제 안내, 작업 도중 바꾼 공개 범위다.
- **연구 도우미와 사용량**은 모델 수나 요금 설명을 결정하기 전에 실행과 차감 기록을 맞춰 볼 필요가 있다. 성공·실패·진행·취소를 요청 집계에 어떻게 포함하는지, 크레딧 지급과 남은 양을 어디에서 세는지 설정과 도우미에 같은 기준으로 표시한다.
